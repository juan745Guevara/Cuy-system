# 8. Estilo arquitectónico

## Estilo elegido

**Monolito modular con Clean Architecture (puertos y adaptadores) en cada módulo**, desplegado como un sistema **cliente-servidor de tres niveles**.

El estilo se aplica en tres niveles de detalle:

| Nivel | Estilo | Qué define |
|---|---|---|
| Sistema | Cliente-servidor en 3 niveles | Frontend web (Next.js) ↔ API REST (NestJS) ↔ Base de datos (PostgreSQL). |
| Backend | Monolito modular | Un solo proceso desplegable, dividido en módulos de negocio con fronteras explícitas. |
| Cada módulo | Clean Architecture (puertos y adaptadores) | Capas concéntricas con dependencias hacia el dominio. |

## Descripción

### Nivel sistema: cliente-servidor

- **Cliente (frontend):** aplicación web en Next.js 15 (App Router) y React 18. Muestra las pantallas, mantiene la sesión y la granja activa, y consume la API mediante axios.
- **Servidor (backend):** API REST en NestJS 12 bajo el prefijo `/api/v1`. Concentra toda la lógica de negocio, la seguridad y el acceso a datos.
- **Datos:** PostgreSQL, con acceso mediante Prisma ORM y consultas SQL parametrizadas (`pg`).

La comunicación es HTTP/JSON. En cada petición el cliente envía el token JWT (`Authorization: Bearer`), la granja activa (`x-farm-id`) y la especie (`x-species-id`).

### Nivel backend: monolito modular

El backend es una sola aplicación, pero se organiza en módulos independientes:

| Módulo | Responsabilidad |
|---|---|
| `platform` | Núcleo común a cualquier especie: autenticación, usuarios y roles, granjas, especies, áreas, jaulas (recintos), animales, pesajes, tratamientos (sanidad), mortalidad y auditoría. |
| `cuyes` | Lógica propia de la crianza de cuyes: catálogos (razas y categorías), empadres, partos, destetes, movimientos y traslados, ventas, inventario, alertas, ranking de reproductores y reportes Excel. |
| `shared` | Núcleo compartido (*shared kernel*): conexión a base de datos, guards de seguridad, decoradores, auditoría, formato de respuesta y reglas de área por especie. |

Reglas entre módulos:

- `cuyes` depende de `platform`, nunca al revés. `platform` no conoce a ninguna especie.
- Ambos dependen de `shared`.
- Una nueva especie (por ejemplo, conejos) se agregaría como un módulo nuevo al mismo nivel que `cuyes`, reutilizando `platform` sin modificarlo.

### Nivel módulo: Clean Architecture

Cada módulo (`platform` y `cuyes`) tiene la misma estructura de cuatro capas:

```text
módulo/
├── presentation/http/         Controladores REST (adaptadores de entrada)
├── application/               Servicios = casos de uso
├── domain/                    Entidades, value objects, errores y puertos
└── infrastructure/persistence Repositorios (adaptadores de salida)
```

- **Presentación:** recibe la petición HTTP, aplica la seguridad (rol, granja) y delega en el caso de uso.
- **Aplicación:** coordina el caso de uso, valida reglas de negocio y registra la auditoría.
- **Dominio:** define los conceptos del negocio y los **puertos**, es decir, las clases abstractas que describen qué datos necesita el caso de uso.
- **Infraestructura:** implementa los puertos con Prisma o SQL.

**Regla de dependencias:** las dependencias apuntan hacia el dominio. El dominio no importa NestJS, Prisma ni infraestructura, y la capa de aplicación nunca importa infraestructura. La unión entre un puerto y su implementación se hace por inyección de dependencias en `platform.providers.ts` y `cuyes.providers.ts`.

## Justificación

### Por qué un monolito modular y no microservicios

1. **Tamaño del equipo y del problema:** el sistema lo desarrolla un equipo pequeño para una sola institución (Facultad de Zootecnia, UNAS). Los microservicios añadirían costos de despliegue, red, observabilidad y consistencia distribuida que no se justifican.
2. **Consistencia transaccional:** operaciones como reubicar animales, registrar un parto con sus crías o cerrar un empadre modifican varias tablas a la vez (animales, jaulas, movimientos). En un monolito se resuelven con una transacción ACID de PostgreSQL. Con microservicios requerirían sagas o compensaciones.
3. **Infraestructura limitada:** un solo servidor de aplicación y una sola base de datos son fáciles de instalar y mantener en un entorno universitario.
4. **Camino de evolución:** las fronteras entre módulos permiten, si algún día hiciera falta, extraer un módulo como servicio independiente.

### Por qué módulos y no un monolito en capas tradicional

Un monolito en capas clásico (todos los controladores, todos los servicios, todos los repositorios juntos) mezcla lo común con lo específico de la especie. Separar `platform` de `cuyes` permite:

- incorporar nuevas especies sin tocar el núcleo
- que cada módulo evolucione y se pruebe por separado
- ubicar rápidamente el código de cada funcionalidad

### Por qué Clean Architecture en cada módulo

1. **Independencia de la tecnología:** los casos de uso dependen de puertos, no de Prisma ni de SQL. Por ejemplo, el paso de consultas SQL a Prisma se hizo cambiando solo los repositorios.
2. **Reglas de negocio protegidas:** las validaciones de negocio viven en la capa de aplicación y el dominio, no en los controladores. Ejemplos: la capacidad de la jaula, el propósito del área, las fechas no futuras y los traslados solo entre granjas de la misma especie.
3. **Capacidad de prueba:** al depender de abstracciones, los casos de uso pueden probarse con repositorios falsos, sin base de datos.
4. **Uniformidad:** todos los módulos siguen la misma estructura, lo que facilita incorporar desarrolladores.

### Alternativas evaluadas

| Alternativa | Ventaja | Motivo de descarte |
|---|---|---|
| Monolito en capas tradicional | Simple al inicio | Mezcla lo común con lo específico de cada especie y dificulta agregar especies. |
| Microservicios | Escalado y despliegue independientes | Complejidad operativa y transacciones distribuidas innecesarias para el tamaño del sistema. |
| Hexagonal pura | Aislamiento total del núcleo | Clean Architecture ya incorpora puertos y adaptadores y además organiza el código en capas, lo que es más claro para el equipo. |
| **Monolito modular + Clean Architecture** | Equilibrio entre simplicidad y extensibilidad | **Elegido.** |

## Limitaciones conocidas (deuda técnica)

La estructura sigue el estilo elegido, pero quedan aspectos por madurar:

- Los puertos de repositorio se declaran con firmas genéricas (`...args: any[]`). Conviene tiparlos.
- El dominio es mayormente anémico: varias reglas viven en los servicios en lugar de en entidades.
- Los servicios devuelven códigos HTTP (`ok(data, 201)`, `fail(msg, 409)`). Lo ideal es que devuelvan errores de dominio y que la presentación los traduzca.
- El módulo `cuyes` consulta directamente tablas de `platform` (`recintos`, `areas`, `granjas`) en lugar de usar una interfaz pública de ese módulo.
